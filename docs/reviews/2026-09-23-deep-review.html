Confirmed findings

The findings below describe behavior present at the reviewed origin/main commit. Each identifies a concrete trigger, its source evidence, and the fix in this PR.

P1 · data integrity

A payment can reference another student's invoice

For POST /api/students/1/payments with an existing invoice owned by student 2, CreatePaymentAsync verifies only that the invoice exists, then inserts a payment for student 1 with student 2's invoice ID. The migration has separate foreign keys for student_id and invoice_id, so it does not reject that combination. Student 1's balance decreases while student 2's invoice is not settled by the invoice-payment query.

Evidence: apps/backend/src/Infrastructure/Billing/BillingService.cs:115–140,165–179; apps/backend/src/Infrastructure/Migrations/Scripts/014_CreatePayments.sql:2–13. Story 6.1 defines student-scoped payment routes.

Fixed: payment creation rejects an invoice whose StudentId differs from the route student. A unit regression test checks the rejected pair.

P1 · financial reliability

The global interceptor retries payment and invoice creation

The interceptor retries every HTTP method after network, timeout, 503, or 504 errors. Billing uses POST for both invoice and payment creation. If the server commits a write and the client receives one of those errors, resubscribing can send the same write up to two more times. The API has no idempotency key for these endpoints, so the student can receive duplicate charges or payments.

Evidence: apps/frontend/src/app/core/interceptors/error.interceptor.ts:25–48; apps/frontend/src/app/core/services/billing.service.ts:50–60,85–92; apps/backend/src/Api/Controllers/BillingController.cs:94,179.

Fixed: automatic retries now apply only to GET and HEAD. An HTTP test checks a payment POST is sent once after a 503 and a GET still retries.

P1 · credential exposure

A failed login logs the submitted password

When the login POST returns 401, the error interceptor passes the entire request body into the log context and enables console logging. The logging service retains that context in error history and prints it with console.error. The login body includes the password, so an ordinary failed sign-in exposes the submitted secret to browser diagnostics and any collected console output.

Evidence: apps/frontend/src/app/core/interceptors/error.interceptor.ts:53–67; apps/frontend/src/app/core/services/error-logging.service.ts:79–99,262–284; apps/frontend/src/app/core/services/auth.service.ts:50–54.

Fixed: generic error context no longer includes request bodies. The failed-login test checks the logger receives no password and the login screen is not redirected again.

P2 · authentication recovery

Error conversion drops the HTTP status callers need

After handling a 401, the error interceptor rethrows an AppError with statusCode rather than the original HttpErrorResponse with status. The outer auth interceptor and AuthService.getCurrentUser() both test error.status === 401. Their cleanup does not run, leaving the expired token in local storage. The route guard sees that token and allows a protected route to activate again.

Evidence: apps/frontend/src/app/core/interceptors/error.interceptor.ts:71; apps/frontend/src/app/models/error.model.ts:36–51; apps/frontend/src/app/core/interceptors/auth.interceptor.ts:22–27; apps/frontend/src/app/core/services/auth.service.ts:119–132; apps/frontend/src/app/core/guards/auth.guard.ts:21–24.

Fixed: the interceptor logs the error and rethrows the original HttpErrorResponse. The auth interceptor clears a session only when it attached a token; anonymous login failures remain on the login screen.

P2 · deployment signals

Fatal API startup errors can exit successfully

A missing production JWT key throws during host setup. The outer catch logs a fatal error but neither rethrows nor sets a nonzero process exit code. The process reaches the end of Program.cs normally, so a supervisor or deployment step that relies on exit status can treat failed startup as success.

Evidence: apps/backend/src/Api/Program.cs:87–89,261–270.

Fixed: the startup catch sets process exit code 1. A missing-key startup was reproduced with exit code 0 before the change and exit code 1 after it.
